# Adoption of bcryptjs for Credential Storage and Verification: Teams Monitor Cpu Utilization During Credential

Status: proposed
Date: 2025-05-18
Deciders: Detection Pipeline (automated)

## Scope Paths

Root: `packages/db`

Applies to:
- `src/utils/**`

## Context

- Authentication mechanisms require persistent verification of client credentials such as API keys without exposing secrets to database compromise.
- Plaintext storage of authentication credentials introduces critical security vulnerabilities where unauthorized data access exposes all consumer secrets.
- The codebase establishes cryptographic token generation and one-way salted hashing within data persistence utilities using crypto and bcryptjs.

## Problem Statement

API key authentication requires generating high-entropy tokens and persisting verifiable proof of those secrets in the database. Storing raw tokens directly exposes consumer credentials to data leaks and internal access threats, whereas insufficient or fast hashing algorithms leave credentials vulnerable to offline brute-force and rainbow table attacks.

## Decision

1. SHOULD: Teams SHOULD monitor CPU utilization during credential authentication workflows and evaluate adjusting bcrypt salt rounds if hardware profiling indicates latency bottlenecks or security baseline changes.

## Policy Block

- SHOULD Teams SHOULD monitor CPU utilization during credential authentication workflows and evaluate adjusting bcrypt salt rounds if hardware profiling indicates latency bottlenecks or security baseline changes.

In scope:
- Generation, persistence, and verification of API key tokens and authentication credentials
- Data layer utilities and service boundaries handling credential storage

Out of scope:
- Short-lived ephemeral session tokens that are validated via digital signatures without database persistence
- Public identification tokens or tenant identifiers that do not serve as authentication secrets

## Rationale

- Adopting bcryptjs provides an established adaptive work-factor hashing algorithm that protects stored credentials against offline dictionary and brute-force attacks.
- Utilizing crypto.randomBytes with 16 bytes guarantees sufficient entropy to prevent token collision and prediction.
- Enforcing bcrypt.compare avoids naive string equality comparisons that are susceptible to timing side-channel attacks.

## Consequences

Positive:
- Database leaks do not expose plaintext consumer API keys or authentication credentials.
- Salted hashing with ten rounds prevents precomputed rainbow table attacks.
- Standardized usage of bcrypt.compare ensures constant-time verification across authentication endpoints.

Negative:
- CPU overhead increases during credential generation and validation due to the computational cost of ten bcrypt salt rounds.
- Plaintext tokens cannot be recovered upon loss and must be regenerated by consumers.

## Alternatives

- Storing raw plaintext tokens directly in the persistence layer (rejected)
  Rejected because: Direct plaintext storage creates severe security vulnerabilities if the database is read or leaked.
  When valid: Never valid for authentication secrets or API key tokens.
- Fast cryptographic digests such as unsalted SHA-256 for credential hashing (rejected)
  Rejected because: Fast hashing algorithms lack computational work factors and permit rapid offline rainbow table and GPU brute-force attacks.
  When valid: Valid for content addressing or non-secret checksum verification, but invalid for credential storage.

## Risks

- High authentication request concurrency may cause thread-pool starvation due to the synchronous or heavy CPU load of bcrypt hashing.
  Mitigation: Ensure asynchronous bcrypt methods are used and implement caching or rate limiting for repeated authentication calls.
  Owner: engineering team
- Future hardware improvements may diminish the defensive efficacy of ten salt rounds against specialized cracking hardware.
  Mitigation: Periodically review computational cost factors and establish migration strategies for re-hashing credentials upon successful authentication.
  Owner: security team

- Always return the generated plaintext token to the client exactly once upon creation, as the unhashed secret cannot be retrieved from the persisted hash.
- Execute credential comparison operations asynchronously to avoid blocking the event loop during password and token verification.

## Continuation Context


Verify commands:
- find . -type f -not -path '*/.*' -exec grep -l "bcrypt.hash" {} +
- find . -type f -not -path '*/.*' -exec grep -l "bcrypt.compare" {} +

Accept when:
- All credential storage utilities invoke bcrypt.hash with ten salt rounds and avoid persisting raw token values.
- All token authentication verification paths use bcrypt.compare for credential validation.

## Enforcement

- Verified by: Automated static analysis and code review checks validating that credential models do not store raw tokens.
- Verified by: Unit and integration test suites validating that stored credentials match bcrypt hash formats and verify through bcrypt.compare.
- Violation handling: Pull requests attempting to persist raw secrets or bypass bcrypt hashing will be blocked in code review.
- Violation handling: Any detected unhashed credential storage requires immediate secret revocation, schema remediation, and token regeneration.
- Exception process: Exceptions require formal security architecture review and signed approval before any non-bcrypt credential storage mechanism may be introduced.
